# 阶段一（v0）设计说明：两个核心流程与关键取舍

> 范围：`rag-from-zero` 阶段一最小可用 RAG。LLM 使用 DeepSeek API（OpenAI 兼容，key 从环境变量读取），Embedding 使用 Ollama bge-m3。
> 阅读前提：已读完《从零构建 RAG 系统实战指南》第 3 章。

---

## 1. 总览：两个流程共享什么

```
【离线：cmd/ingest】                        【在线：cmd/server】
data/docs/*.md                             用户问题（stdin）
    ↓ loader.LoadDir                         ↓ embedder.Embed（同一个！）
[]Document {Content, Source, Title}        query 向量
    ↓ chunker.Split                          ↓ vectorstore.Search（余弦 Top-K）
[]Chunk {ID, Text, Source, Heading, Index} []ScoredChunk
    ↓ embedder.Embed（批量+并发+重试）        ↓ renderPrompt（text/template）
[]Entry {Chunk, Vector}                    ↓ llm.Chat（DeepSeek）
    ↓ store.Add + SaveToFile               Answer {Text, Sources, RetrieveMs, GenerateMs}
data/index.json
```

**第一原则：离线和在线必须使用同一个 embedder 实例、同一份预处理逻辑。** 向量空间由模型决定，换模型或换预处理，旧索引全部作废。这也是 embedder 被抽成独立组件、被两个 cmd 共同引用的原因。

## 2. 离线流程（cmd/ingest）：解析 → 分块 → Embedding → 入库

代码：`cmd/ingest/main.go`，四个阶段各对应一次明确的日志输出。

### 2.1 解析（loader）

调用链：`LoadDir(dir, MarkdownLoader{})` → `filepath.WalkDir` 按扩展名分发 → `os.ReadFile` → `extractTitle`（第一个 `# ` 行，无则回退文件名）。

- 只认 `.md` / `.markdown`，其他文件静默跳过——**控制变量，一次只引入一个复杂度**（PDF/Word 是阶段二的事）。
- 返回按路径排序，保证索引构建**可复现**（同样的输入产出同样的 index.json）。

### 2.2 分块（chunker）

`Chunker{MaxSize, Overlap}.Split(doc)` 两阶段切分：

1. **结构感知**：按 `## ` 级标题把文档切成 section；第一个标题之前的前言归属文档标题。标题行本身不进入正文（避免噪音词污染向量）。
2. **长度兜底**：section 超长时，`splitLongText` 在 `maxSize` 窗口内**从后往前**找切点——优先级：空行（段落边界）> 句子边界（。！？；）> 硬切字符。相邻块回退 `overlap` 字符，保证语义连贯。

Chunk 从第一天就携带 `Source` / `Heading` / `Index`。v0 觉得元数据没用，等到生成答案要标注引用时就晚了。

### 2.3 Embedding（embedder）

`OllamaEmbedder.Embed(ctx, texts)` 内部三件套：

| 机制 | 参数 | 默认值 | 解决什么 |
|---|---|---|---|
| 分批 | `batchSize` | 32 | 一次请求传 32 条比逐条快一个数量级 |
| 并发限流 | `concurrency`（semaphore） | 4 | 本地 Ollama 也有吞吐上限，防打满 |
| 重试 | `maxRetries`（指数退避） | 3 | 网络抖动是常态，Embedding 幂等，放心重试 |

关键实现细节：**结果按 `batch{start, texts}` 的起始偏移写回 `results` 切片，保证输出顺序与输入一致**——并发不改变语义。

### 2.4 入库（vectorstore）

`MemoryStore.Add` 纯内存追加；`SaveToFile` 用 JSON 序列化，**先写 `.tmp` 再 `os.Rename`**——索引文件不会被写一半的状态截断。server 端 `LoadFromFile` 对"文件不存在"返回空库而非报错（但 server 启动时显式拒绝空索引）。

## 3. 在线流程（cmd/server）：检索 → 生成

代码：`cmd/server/main.go` 的 REPL 循环 → `pipeline.Answer(ctx, question)`。

### 3.1 检索（pipeline.Answer 前半段）

1. `embedder.Embed(ctx, []string{question})` —— 与索引用**同一个 embedder 配置**（同模型、同地址），这是向量空间对齐的具体落实点。
2. `store.Search(qVec[0], topK)` —— 全量扫描算余弦相似度，降序取前 K。**几千块语料毫秒级，不要为用不到的规模提前引入 ANN**。

### 3.2 生成（pipeline.Answer 后半段）

1. `renderPrompt`：用 `text/template` 渲染 RAG Prompt 模板（`internal/pipeline/rag.go`）。要点：
   - 强约束："只能使用参考资料中的信息，禁止使用你自己的知识"；
   - 明确拒答："资料不足时回答'根据现有资料无法回答'"；
   - 每个 chunk 自带 `[来源: 文件名 章节]` 标注，让模型照着格式引用。
2. `llm.Chat`：DeepSeek `POST /chat/completions`，OpenAI 格式。错误处理分两类：**429/5xx 指数退避重试（最多 3 次）；其他 4xx 直接失败不重试**——400 重试多少次都是 400。
3. 返回结构化 `Answer{Text, Sources, RetrieveMs, GenerateMs}`。引用溯源是 RAG 区别于裸模型的核心价值；耗时字段从第一天就记录，线上排障"是检索错了还是生成错了"全靠它。

### 3.3 Prompt 的角色划分

v0 把完整资料放在 system 消息里，用户问题放在 user 消息。模板单独成常量而非散落的字符串拼接——**Prompt 是核心资产，变更应像代码一样可追踪、可 diff、可回滚**。

## 4. 关键设计决策清单

| 决策 | 选择 | 理由 / 代价 |
|---|---|---|
| 离线/在线分离 | 两个 cmd 共享 internal/ | 两者生命周期、失败策略完全不同；共享组件但不共享进程 |
| 接口抽象 | `Loader` / `Embedder` / `LLM` 均为接口 | 模型供应商变化远快于代码；换实现不动 pipeline |
| 向量库 v0 | 内存 + 暴力余弦 | 先理解本质（相似度排序）再引入 HNSW；JSON 落盘即可恢复 |
| LLM 配置 | `DEEPSEEK_API_KEY` 等环境变量 | key 不进代码库；baseURL/model 可一键切换（也兼容代理） |
| 拒答设计 | Prompt 强约束 + 资料中标注来源 | 无答案问题（验收标准要求）依靠模型自觉，v1 可加 score 阈值兜底 |
| 索引落盘 | JSON + 临时文件 rename | 原子写；代价是文件比 gob 大，v1 换 sqlite-vec 时自然解决 |

## 5. Embedding 环节：可调、可测、可优化的取舍点

### 5.1 分块参数（效果第一决定因素）

- **`MaxSize`（默认 512 字符）**：太小 → 语义碎、向量被单句噪音主导；太大 → 一个 chunk 塞多个主题、相似度被稀释。**中文按字符不按词**。
- **`Overlap`（默认 50，约 10%）**：换块处上下文断裂的补偿。过大的 overlap 会让相邻块向量高度相似、挤占 Top-K 名额（5 个结果里 3 个是同一节的重复内容）。
- **调优方法（先做这个实验）**：固定 3~5 个你已知答案的问题，把 chunk size 分别改成 100 / 512 / 2000，打印每次检索的 Top-5 chunk 全文，人工判断"正确的 chunk 有没有被召回"。**没有评估的调优都是玄学**——这就是阶段三评测集的雏形。

### 5.2 切分边界策略

当前优先级：段落 > 句子 > 硬切。已知弱点：

- 代码块、表格会被句子边界切碎（`。` 在代码里少见，但表格行会断）。v1 应把 ``` 围栏代码块和表格作为**原子单元**整体保留（超长时宁可整块超一点）。
- `#` 级标题不参与切分（只认 `##`）。对短文档没问题，长文档可改为按任意级别标题切。

测试点：`chunker_test.go` 已覆盖标题切分、超长切分、overlap 连续性；新增策略时应补"代码块不被切碎"的用例。

### 5.3 Embedding 吞吐参数

- `batchSize` / `concurrency`：本地 Ollama 的甜蜜点需要实测。症状对照：** embedding 阶段频繁超时** → 降 concurrency；**CPU 占用低、耗时长** → 升 concurrency 或 batchSize。
- 测试点：`embedder_test.go` 用 mock server 验证了分批数量（7 条 / batch 3 = 3 次请求）和**乱序并发下输出顺序不变**。改调度逻辑时这两个测试必须继续过。

### 5.4 模型选择（最贵的决定）

换 Embedding 模型 = 维度可能变 + 向量空间变 = **全量重建索引**。bge-m3（1024 维，中英双语）是当前默认；换成任何 API 化 embedding（如 OpenAI text-embedding-3）时，只换 `embedder` 实现，pipeline 不动——这是接口抽象的回报。

另一个隐蔽点：**query 和文档必须走同一预处理**。如果未来在索引入库前做了去 HTML、全角转半角等清洗，检索端 query 必须做同样的清洗，否则空间错位。

## 6. 检索环节：可调、可测、可优化的取舍点

### 6.1 Top-K

- 默认 5。进 Prompt 的 chunk 越多 → 上下文越全，但噪音越多、越贵、越容易"Lost in the Middle"（正确答案被埋在中间，模型注意力衰减）。
- DeepSeek 长上下文给了调优空间：可以试 Top-10/20，用阶段三评测集对比效果与 token 成本。**这是"了解自己模型供应商"的工程实践。**
- 可考虑分数阈值兜底：Top-1 相似度低于阈值（如 0.3）时直接拒答，比纯靠 Prompt 自觉更可靠。阈值需在真实语料上统计分布后定。

### 6.2 暴力扫描 → ANN 的升级时机

当前全量扫描。升级信号：**检索耗时 > 100ms 且语料 > 10 万块**。在此之前引入 HNSW 只增加复杂度，不增加理解。升级点收敛在 `vectorstore` 包的 `Search` 一个方法内（阶段二会抽 `VectorStore` 接口）。

### 6.3 向量检索的已知盲区 → 混合检索

纯向量对**专有名词、产品型号、错误码、人名**不敏感（embedding 学的是语义分布，不是精确匹配）。课程文档里的"Raft"、"2PC"、"TCC"这类术语检索质量需要人工抽查验证。

阶段二方案：bleve 建 BM25 索引，与向量结果用 **RRF（排名融合，`1/(60+rank)`）** 合并——不用分数直接相加（量纲不同，融合结果会异常）。**混合检索通常是投入产出比最高的单项优化**，用评测数据验证。

### 6.4 粗排 → 重排

向量检索是双塔结构，query 和文档独立编码，精度有天花板。阶段二：粗排取 30 → cross-encoder 重排（Ollama 跑 `bge-reranker-v2-m3`）→ 精选 5 进 Prompt。粗排 K / 重排 N / 进 Prompt 数量三个参数**全部抽成配置**，阶段三反复调。

### 6.5 检索质量的测试方法（现在就能做）

**调试第一原则：先分离检索问题和生成问题。** 遇到"回答质量差"：

```
① 直接看检索结果（绕过生成）：正确的 chunk 被召回了么？
   ├─ 没有 → 检索问题：查分块质量、embedding、上混合检索
   └─ 有 → ② 看 Prompt 组装：正确 chunk 进 Prompt 了么？位置被埋中间了吗？
              └─ 有且位置好 → ③ 生成问题：Prompt 约束 / 模型能力 / 截断
```

v0 立即可做的手动验证：在 `pipeline.Answer` 里加一行 debug 日志打印 Top-K chunk ID，对 10 个已知答案的问题逐一核对召回。**阶段三的 HitRate@K 评测集就是这个流程的自动化。**

## 7. v0 验收对照

| 验收标准 | 现状 | 验证方式 |
|---|---|---|
| 索引 10 篇文档无报错 | ✅ 单测覆盖 + `go run ./cmd/ingest` | 33 篇文档实测 |
| 文档中明确有的问题回答正确且带来源 | Prompt 含引用格式约束 | 交互问答人工核对 `[来源: ...]` |
| 文档中没有的问题回答"无法回答" | 依赖 Prompt 约束（无阈值兜底） | 故意提问无关问题观察 |
| 检索/生成耗时有日志 | `Answer.RetrieveMs / GenerateMs` | server 每次问答输出 |
